# Текст для защиты проекта MatchService

## Слайд 2. Назначение микросервиса

Микросервис MatchService позволяет управлять матчами и связанными сущностями в системе проведения турниров. Функциональность разделена по ролям пользователей.

### Администратор

Администратор — пользователь системы с правами на организацию и управление матчами.

Администратор выполняет следующие операции:

- создаёт матчи для определённых турнира и турнирной сетки;
- выбирает первого и второго участника;
- не может создать матч, если оба идентификатора игрока совпадают;
- планирует время проведения матча;
- переводит матч из состояния `Scheduled` в `InProgress`;
- указывает сервер и название карты;
- изменяет допустимые поля в зависимости от состояния матча;
- вводит победителя и счёт каждого игрока;
- завершает матч и переводит его в состояние `Completed`;
- оспаривает или отменяет матч;
- удаляет матч из коллекции своих матчей.

В доменной модели операции выполняются через класс `Administrator`. Перед выполнением каждого действия класс проверяет, что матч принадлежит этому администратору. Если совпадение не найдено, вызывается доменное исключение `MatchNotFoundException`.

### Пользователь

Пользователь может быть одним из двух участников матча.

Пользователь выполняет следующие действия:

- просматривает свои данные и данные других пользователей через API;
- является участником матча;
- после завершения матча может оспорить результат;
- не может оспорить матч, если он не является ни первым, ни вторым игроком.

Текущее REST API предоставляет пользователям CRUD-операции для сущности `User`. Доменный сценарий оспаривания реализован в методе `User.DisputeMatch` и в методе `Match.Dispute`.

## Слайд 3. ER-модель базы данных

`MatchService` использует PostgreSQL и Entity Framework Core. База данных содержит таблицы для пользователей, администраторов, турниров, турнирных сеток и матчей.

Основные сущности базы данных:

- `Administrators` — администраторы матчей;
- `Users` — пользователи платформы;
- `Tournaments` — турниры;
- `Brackets` — турнирные сетки;
- `Matches` — матчи.

Один администратор может управлять несколькими матчами. Турнир содержит несколько сеток, а сетка может быть связана с несколькими матчами. Один матч содержит ссылки на одного администратора, один турнир, одну сетку и двух пользователей.

Поля таблицы `Matches`:

- `Id`;
- `AdministratorId`;
- `TournamentId`;
- `BracketId`;
- `Player1Id`;
- `Player2Id`;
- `WinnerId`;
- `Status`;
- `ScheduledTime`;
- `StartedAt`;
- `CompletedAt`;
- `CreatedAt`;
- `MapName`;
- `ServerInfo`;
- `Player1Score`;
- `Player2Score`.

Связи обеспечиваются внешними ключами. Для ключевых связей используется ограничение `Restrict`, то есть при удалении администратора, турнира, сетки или игрока удаление не выполняется каскадно. Для связи с победителем используется `SetNull`: при удалении пользователя поле `WinnerId` сбрасывается в `null`.

Статус матча хранится в базе как строка. Объекты-значения `MapName`, `ServerInfo` и счёт игрока преобразуются EF Core в обычные колонку или типы базы данных.

## Сценарий защиты — видео 1

MatchService — это REST API-сервис для работы с матчами, администраторами и пользователями платформы VirtuSphere.

Решение разделено на слои и отдельные проекты:

- `MatchService.Domain` описывает доменную модель;
- `MatchService.ValueObjects` содержит объекты-значения и валидаторы;
- `MatchService.Domain.Repositories.Abstractions` содержит интерфейсы репозиториев;
- `MatchService.Application.Models` содержит DTO-модели;
- `MatchService.Application.Services` содержит application-сценарии;
- `MatchService.Infrastructure.EntityFramework` реализует работу с PostgreSQL;
- `MatchService.WebHost` является точкой входа и предоставляет REST API;
- `MatchService.Tests` содержит модульные и интеграционные тесты.

Это отдельный REST-сервис в составе микросервисной платформы. Внутри приложение разделено на слои, поэтому HTTP-контроллеры не содержат доменной логики.

## Сценарий защиты — видео 2

Проект написан на C# с использованием .NET 8. REST API реализован в ASP.NET Core.

Для работы с данными используются Entity Framework Core и Npgsql. СУБД проекта — PostgreSQL. AutoMapper преобразует доменные сущности в DTO-модели, а Swagger предоставляется для просмотра и вызова HTTP-методов.

Строка подключения задаётся в `appsettings.json`. При запуске приложения создаётся `ApplicationDbContext`, регистрируются репозитории и application-сервисы.

Схема базы данных обновляется с помощью миграций Entity Framework Core. В проекте хранится начальная миграция и снимок модели базы данных. При старте приложения вызывается метод `Database.Migrate()`, поэтому ожидающие миграции применяются автоматически.

Для работы с миграциями используются стандартные команды:

```powershell
dotnet ef migrations add <ИмяМиграции>
dotnet ef database update
```

Проекты следует запускать с указанием startup-проекта WebHost и проекта инфраструктуры.

## Сценарий защиты — видео 3

Доменный слой описывает предметную область и не зависит от ASP.NET Core и PostgreSQL.

### Класс Match

Класс `Match` является корнем агрегата и наследуется от `Entity<Guid>`. Он содержит:

- идентификаторы турнира, сетки и администратора;
- ссылки на двух игроков;
- ссылку на победителя;
- статус матча;
- время создания, планирования, старта и завершения;
- название карты;
- сведения о сервере;
- счёт обоих игроков.

Жизненный цикл регулируется методами `Schedule`, `Start`, `SubmitResult`, `Edit`, `Dispute` и `Cancel`. Каждый метод проверяет текущее состояние матча и возвращает доменное исключение при недопустимом переходе.

Например, метод `Start` разрешён только в состоянии `Scheduled`. Метод `SubmitResult` выполняется только в состоянии `InProgress`, а победитель должен совпадать с одним из участников.

### Класс Administrator

Класс `Administrator` наследуется от `Entity<Guid>`. Он содержит объект-значение `Username` и приватную коллекцию `_matches`.

Через метод `CreateMatch` администратор создаёт матч. Методы `StartMatch`, `SubmitMatchResult`, `RescheduleMatch`, `EditMatch`, `CancelMatch`, `DisputeMatch` и `DeleteMatch` сначала проверяют наличие матча в коллекции администратора.

Такая проверка отображает правило принадлежности: администратор не должен выполнять операцию над матчем из другой административной коллекции.

### Объекты-значения

Для типизации и защиты данных используются объекты-значения:

- `Username` — от 3 до 30 символов;
- `MapName` — от 3 до 30 символов;
- `ServerInfo` — не пустая строка длиной до 120 символов;
- `PlayerScore` — целое число от 0 до 999.

При нарушении правил создаются специализированные доменные или объектно-значимые исключения.

## Сценарий защиты — видео 4

В проекте реализован отдельный тестовый проект `MatchService.Tests`.

Тесты проверяют:

- жизненный цикл матча;
- создание и удаление матчей;
- правила объектов-значений;
- доступ администратора к матчам;
- application-сервисы;
- работу контроллеров;
- работу репозиториев;
- сопоставление DTO-моделей.

Репозитории тестируются с SQLite в режиме in-memory. Это позволяет проверять конфигурации EF Core и SQL-запросы без подключения к реальной PostgreSQL-базе.

По актуальному отчёту о покрытии выполнено 67 тестов, и все они прошли.

Основные показатели последнего отчёта:

- покрытие строк — 98.5%;
- покрытие ветвей — 87.5%;
- анализировано 610 покрываемых строк;
- покрыто 601 строка;
- проанализировано 58 классов.

Отчёт `ReportGenerator` хранится в папке `coverage-report`. GitHub Actions запускает сборку, тесты и сбор покрытия при push и pull request.

GitHub Actions настроен в файле `.github/workflows/ci.yml`. Конвейер запускается автоматически при отправке изменений в любую ветку и при создании pull request. К конвейеру также можно обратиться вручную через интерфейс GitHub Actions.

Рабочий процесс выполняет следующие шаги:

1. загружает исходный код репозитория;
2. устанавливает .NET 8 на виртуальной машине Ubuntu;
3. выполняет `dotnet restore` для решения;
4. собирает решение в конфигурации `Release`;
5. запускает тестовый проект `MatchService.Tests`;
6. собирает отчёт о покрытии в формате Cobertura;
7. проверяет фактический показатель line coverage;
8. загружает отчёт в виде артефакта GitHub Actions.

В конвейер добавлена проверка порога 95% по line coverage. Если фактическое покрытие окажется ниже порога, рабочий процесс завершается с ошибкой. Если тесты падают или решение не собирается, последующие шаги качества также не считаются пройденными.

## Сценарий защиты — видео 5

Покажем создание матча в Swagger.

Сначала создаём администратора через:

```http
POST /api/administrators
```

Например:

```json
{
  "username": "TournamentAdmin"
}
```

Затем создаём первого и второго пользователя через:

```http
POST /api/users
```

После этого создаём турнир и сетку. В текущей реализации для этого нет собственных HTTP-контроллеров, поэтому связанные сущности создаются тестовыми или служебными сценариями или заранее загружаются в базу.

Дальше вызывается:

```http
POST /api/matches
```

Тело запроса содержит идентификаторы:

```json
{
  "tournamentId": "guid",
  "bracketId": "guid",
  "administratorId": "guid",
  "player1Id": "guid",
  "player2Id": "guid"
}
```

Контроллер передаёт `CreateMatchModel` в `IMatchApplicationService`.

Application-сервис загружает турнир, сетку, администратора и двух игроков из репозиториев. Если хотя бы одна сущность отсутствует, он возвращает `null`, а контроллер формирует `400 Bad Request`.

Если все сущности найдены, вызывается:

```csharp
administrator.CreateMatch(tournament, bracket, player1, player2)
```

Созданный матч сохраняется методом репозитория `AddAsync`. В базе появляется запись со статусом `Scheduled`.

При успешной операции API возвращает `201 Created` и DTO-модель матча.

Получить список матчей можно запросом:

```http
GET /api/matches
```

Получить конкретный матч:

```http
GET /api/matches/{id}
```

Удалить матча можно запросом:

```http
DELETE /api/matches/{id}
```

В таблице `Matches` можно проверить сохранённые идентификаторы, статус `Scheduled` и время создания.

## Сценарий защиты — видео 6

Итоговая цепочка обработки создания матча выглядит следующим образом:

```text
Swagger / HTTP-клиент
        ↓
MatchesController
        ↓
MatchApplicationService
        ↓
Репозитории и загрузка связанных сущностей
        ↓
Administrator.CreateMatch
        ↓
Match — проверка доменных инвариантов
        ↓
EfMatchRepository
        ↓
Entity Framework Core
        ↓
PostgreSQL
```

Контроллер отвечает за HTTP-протокол и коды состояния. Application-сервис координирует работу репозиториев и доменных методов. Доменный класс проверяет инварианты матча. EF Core преобразует сущности в записи базы данных.

Основные сценарии покрываются тестами, а GitHub Actions автоматически собирает решение, запускает тесты и проверяет порог покрытия строк.

Таким образом, проект MatchService демонстрирует применение:

- Domain-Driven Design;
- слоистой архитектуры;
- объектов-значений;
- репозиториев;
- Entity Framework Core;
- ASP.NET Core REST API;
- PostgreSQL;
- миграций базы данных;
- модульного тестирования;
- автоматической проверки качества в CI.
