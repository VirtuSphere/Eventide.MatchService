3.3 Доменный слой (Domain Layer)

Доменный слой является ядром микросервиса `MatchService` и инкапсулирует всю бизнес-логику, связанную с проведением матчей. Он определяет основные сущности, их поведение и правила взаимодействия, полностью изолируясь от технических деталей, таких как база данных или пользовательский интерфейс. Этот слой спроектирован с использованием тактических паттернов Domain-Driven Design (DDD).

### 3.3.1 Сущности (Entities)

Сущности — это объекты, обладающие уникальным идентификатором и жизненным циклом. Они представляют ключевые понятия предметной области.

#### 3.3.1.1 Match

Сущность `Match` является корнем агрегата и центральным элементом доменной модели. Она объединяет все данные и правила, связанные с одной игровой встречей. `Match` контролирует жизненный цикл матча через смену статусов и гарантирует целостность данных на каждом этапе.

Поля `Match` (основные):

- `Id` — `Guid`: Уникальный идентификатор матча (PRIMARY KEY).
- `Tournament` — `Tournament`: Ссылка на сущность турнира, в рамках которого проходит матч.
- `Bracket` — `Bracket`: Ссылка на сущность сетки, к которой принадлежит матч.
- `Administrator` — `Administrator`: Ссылка на администратора, создавшего и управляющего матчем.
- `Player1`, `Player2` — `User`: Ссылки на двух игроков, участвующих в матче.
- `Winner` — `User?`: Ссылка на победившего игрока; может быть `null`.
- `Status` — `MatchStatus` (enum): Текущий статус матча (`Scheduled`, `InProgress` и т.д.).
- `ScheduledTime` — `DateTime?`: Запланированное время начала матча.
- `StartedAt`, `CompletedAt` — `DateTime?`: Фактическое время начала и завершения.
- `MapName` — `MapName?` (value object): Название карты, на которой проходит матч.
- `ServerInfo` — `ServerInfo?` (value object): Информация о сервере.
- `Player1Score`, `Player2Score` — `PlayerScore?` (value object): Счет игроков.

При создании `Match` конструктор проверяет, что игроки `Player1` и `Player2` не являются одним и тем же пользователем, выбрасывая исключение `MatchPlayerSameException` в противном случае. Методы `Start()`, `SubmitResult()`, `Dispute()` и `Cancel()` реализуют конечный автомат состояний матча, обеспечивая выполнение бизнес-правил.

#### 3.3.1.2 User

Сущность `User` представляет участника системы — игрока. В контексте `MatchService` её основная роль — быть участником матча. Сущность содержит идентификатор и имя пользователя.

`User` также инкапсулирует поведение, специфичное для игрока. Например, метод `DisputeMatch(Match match)` позволяет игроку оспорить результат завершенного матча, предварительно проверив, что матч находится в статусе `Completed`.

Поля `User` (основные):

- `Id` — `Guid`: Уникальный идентификатор пользователя (PRIMARY KEY).
- `Username` — `Username` (value object): Имя пользователя.

#### 3.3.1.3 Administrator

Сущность `Administrator` выступает в роли фасада или оркестратора для операций над матчами. Администратор создает матчи, назначает время, запускает их, фиксирует результаты и обрабатывает спорные ситуации.

В текущей реализации `Administrator` содержит приватную коллекцию `_matches`, чтобы гарантировать, что он может управлять только "своими" матчами. При вызове методов `StartMatch`, `CancelMatch` и других, выполняется проверка принадлежности матча данному администратору.

Поля `Administrator` (основные):

- `Id` — `Guid`: Уникальный идентификатор администратора (PRIMARY KEY).
- `Username` — `Username` (value object): Имя пользователя администратора.
- `_matches` / `Matches` — `IReadOnlyCollection<Match>`: Коллекция матчей, управляемых администратором.

#### 3.3.1.4 Tournament и Bracket

На данном этапе разработки сущности `Tournament` и `Bracket` реализованы в минималистичном виде. Они представлены классами, содержащими только уникальный идентификатор `Id`. Это сделано для того, чтобы зарезервировать место в доменной модели и установить связи с сущностью `Match`, не перегружая `MatchService` логикой управления турнирами и сетками, которая должна находиться в смежных микросервисах.

### 3.3.2 Перечисления (Enums)

Перечисления используются для определения строго типизированных и семантически ясных наборов состояний.

- `MatchStatus`
    - **Значения**: `Scheduled`, `InProgress`, `Completed`, `Disputed`, `Cancelled`.
    - **Назначение**: Описывает полный жизненный цикл матча. На основе этого перечисления построена логика переходов между состояниями в методах сущности `Match`. Например, начать матч (`Start`) можно только из статуса `Scheduled`.

### 3.3.3 Объекты-значения (Value Objects)

В проекте активно используется паттерн Value Object для представления простых по своей структуре, но обладающих бизнес-логикой и правилами валидации, атрибутов. Объекты-значения являются неизменяемыми (immutable) и их равенство определяется на основе значений их свойств, а не по идентификатору.

Все объекты-значения наследуются от базового класса `ValueObject<T>`, который инкапсулирует логику валидации при создании через интерфейс `IValidator<T>` и реализует корректное сравнение.

#### 3.3.3.1 Подробное описание Value Objects

- `Username` (внутренний тип: `string`)
    - **Назначение**: Хранит имя пользователя (игрока или администратора).
    - **Валидация**: `UsernameValidator` проверяет максимальную длину строки.

- `MapName` (внутренний тип: `string`)
    - **Назначение**: Хранит название игровой карты.
    - **Валидация**: `MapNameValidator` проверяет, что строка не пустая и её длина находится в диапазоне от 3 до 30 символов.

- `ServerInfo` (внутренний тип: `string`)
    - **Назначение**: Хранит информацию о сервере (например, IP-адрес и порт).
    - **Валидация**: `ServerInfoValidator` проверяет, что строка не пустая и её длина не превышает 120 символов.

- `PlayerScore` (внутренний тип: `int`)
    - **Назначение**: Хранит счёт игрока в матче.
    - **Валидация**: `PlayerScoreValidator` проверяет, что значение находится в диапазоне от 0 до 999.

#### 3.3.3.2 Value Objects: валидация и исключения

Система валидации объектов-значений построена на связке `ValueObject<T>` и `IValidator<T>`. При создании любого объекта-значения его конструктор немедленно вызывает метод `Validate` соответствующего валидатора. Если данные не соответствуют правилам, валидатор выбрасывает специализированное исключение.

Основные исключения для объектов-значений (пространство имён `MatchService.ValueObjects.Exceptions`):

- `ValidatorNullException`: Выбрасывается, если в конструктор `ValueObject<T>` не был передан валидатор.
- `ArgumentNullOrWhiteSpaceException`: Используется для строковых VO, если передана пустая строка или `null`.
- `ArgumentShortValueException` / `ArgumentLongValueException`: Выбрасываются, если длина строки меньше минимальной или больше максимальной.
- `PlayerScoreOutOfRangeException`: Сигнализирует, что счёт игрока вышел за пределы допустимого диапазона (0-999).
- `ServerInfoNullOrWhiteSpaceException` / `ServerInfoTooLongException`: Аналогичные строковым исключениям, но специфичные для `ServerInfo`.

Такой подход гарантирует, что в системе не могут существовать некорректные объекты-значения, что значительно повышает надёжность бизнес-логики.

### 3.3.4 Доменные исключения

Доменные исключения служат для явного оповещения о нарушении бизнес-правил. В отличие от системных ошибок, они являются ожидаемой частью работы домена и несут семантическую нагрузку. Все они наследуются от базового класса `DomainException`.

Основные доменные исключения и их назначение:

- `MatchPlayerSameException`: Выбрасывается при попытке создать матч, где оба игрока — один и тот же пользователь.
- `MatchNotScheduledException`: Сигнализирует о попытке выполнить действие (например, `Start`), требующее, чтобы матч был в статусе `Scheduled`, в то время как он находится в другом статусе.
- `MatchNotInProgressException`: Аналогично предыдущему, но для действий, требующих статус `InProgress` (например, `SubmitResult`).
- `MatchWinnerNotParticipantException`: Выбрасывается при попытке указать в качестве победителя пользователя, который не является участником матча.
- `InvalidMatchStatusException`: Общее исключение для недопустимого статуса матча при выполнении операции.
- `MatchNotFoundException`: Используется в слое приложения или в сущности `Administrator` для указания, что матч с заданным ID не найден или не принадлежит администратору.
- `ArgumentNullValueException`: Выбрасывается, когда в метод передается `null` вместо ожидаемого объекта.

### 3.3.5 Интерфейсы репозиториев

Для отделения доменного слоя от способа хранения данных используется паттерн "Репозиторий". Абстракции репозиториев определены в доменном слое, а их реализация находится в слое инфраструктуры.

Базовый интерфейс `IRepository<TEntity, TId>`:

Этот обобщенный интерфейс определяет стандартный набор операций для работы с любой сущностью:

- `Task<TEntity?> GetByIdAsync(TId id, ...)`: Получение сущности по идентификатору.
- `Task<IEnumerable<TEntity>> GetAllAsync(...)`: Получение всех сущностей.
- `Task<bool> ExistsAsync(TId id, ...)`: Проверка существования сущности.
- `Task AddAsync(TEntity entity, ...)`: Добавление новой сущности.
- `Task UpdateAsync(TEntity entity, ...)`: Обновление существующей сущности.
- `Task DeleteAsync(TEntity entity, ...)`: Удаление сущности.

Специализированные интерфейсы:

- `IUserRepository`, `IAdministratorRepository`: Эти интерфейсы наследуются от базового `IRepository` и могут добавлять специфичные для `User` и `Administrator` методы поиска (например, `GetByUsernameAsync`).

Такая структура позволяет доменной логике работать с данными через абстракции, не имея представления о том, как и где они хранятся (в PostgreSQL, в памяти или где-то еще).

## 3.4 Слой инфраструктуры (Infrastructure Layer)

Инфраструктурный слой содержит реализацию технических аспектов приложения, которые были абстрагированы в доменном слое. В данном проекте он отвечает за взаимодействие с базой данных PostgreSQL с помощью ORM Entity Framework Core.

### 3.4.1 Контекст базы данных ApplicationDbContext

`ApplicationDbContext` является основной точкой входа для работы с базой данных. Этот класс наследуется от `Microsoft.EntityFrameworkCore.DbContext` и выполняет следующие функции:

- **Определение наборов данных (DbSet)**: Содержит свойства `DbSet<T>` для каждой из основных сущностей: `Users`, `Administrators`, `Matches`, `Tournaments`, `Brackets`. Через эти свойства выполняются все запросы к соответствующим таблицам.
- **Конфигурация модели**: В методе `OnModelCreating` вызывается `modelBuilder.ApplyConfigurationsFromAssembly(GetType().Assembly)`. Этот подход позволяет EF Core автоматически найти и применить все конфигурации сущностей, определенные в сборке, что делает код `DbContext` чистым и лаконичным.
- **Настройка подключения**: Конструктор `ApplicationDbContext` принимает `DbContextOptions`, что позволяет настраивать подключение к базе данных извне, через систему внедрения зависимостей (DI).

### 3.4.2 Конфигурация сущностей через Fluent API

Для детальной настройки того, как доменные сущности отображаются на таблицы базы данных, используется Fluent API. Конфигурация для каждой сущности вынесена в отдельный класс, реализующий интерфейс `IEntityTypeConfiguration<T>`. Это обеспечивает модульность и чистоту кода.

Ключевые аспекты конфигураций:

- **Отображение Value Objects**: Для каждого объекта-значения настроен конвертер (`HasConversion`). Например, `MapName` конвертируется в `string` и обратно, а для поля в базе данных задается максимальная длина (`HasMaxLength`).
    ```csharp
    // Пример для MapName в MatchConfiguration.cs
    builder.Property(m => m.MapName)
        .HasConversion(
            mapName => mapName.Value,
            str => new MapName(str))
        .HasMaxLength(MapNameValidator.MAX_LENGTH);
    ```
- **Отображение перечислений (Enums)**: Статус матча `MatchStatus` сохраняется в базе данных как строка (`HasConversion<string>()`), что улучшает читаемость данных при прямом просмотре таблиц.
- **Настройка связей (Relationships)**: Четко определены внешние ключи и поведение при удалении. Например, связь `Match` с `User` (как `Player1`, `Player2`, `Winner`) настроена с `ON DELETE SET NULL` для победителя, чтобы удаление пользователя не приводило к ошибкам в старых матчах.
- **Индексы**: Для полей, по которым часто будет производиться фильтрация (например, `Status`), созданы индексы для повышения производительности запросов.

### 3.4.3 Миграции (Migrations)

Управление версиями схемы базы данных осуществляется с помощью механизма миграций EF Core. Все миграции хранятся в папке `Infrastructure/MatchService.Infrastructure.EntityFramework/Migrations`.

- **Процесс работы**: При изменении доменной модели или конфигураций EF Core, разработчик создает новую миграцию с помощью команды `dotnet ef migrations add <MigrationName>`. Эта команда анализирует различия между текущим состоянием модели (зафиксированным в файле `ApplicationDbContextModelSnapshot.cs`) и новым состоянием, после чего генерирует C#-код для обновления схемы БД (метод `Up`) и ее отката (метод `Down`).
- **Применение миграций**: Миграции применяются к базе данных командой `dotnet ef database update`. В проекте также реализован вспомогательный класс `MigrationManager.cs` в `MatchService.WebHost`, который автоматически применяет все недостающие миграции при старте приложения. Это удобно для сред разработки и тестирования, но в продуктивной среде рекомендуется применять миграции через контролируемый CI/CD-пайплайн.
- **Снимок модели**: Файл `ApplicationDbContextModelSnapshot.cs` является критически важным артефактом. Он представляет собой полное кодовое представление текущей схемы базы данных и служит источником для создания новых миграций. Он должен всегда находиться в актуальном состоянии и храниться в системе контроля версий.
